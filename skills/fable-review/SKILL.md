# fable-review: 저렴한 수집, Fable 판단, 항목별 질문

입력: $ARGUMENTS (검토 범위나 추가 관점, 없으면 커밋 안 된 변경 전체)

흐름은 **범위 정리 -> 병렬 수집 -> Fable 판단 -> 자동 수정 -> 항목별 질문 -> 반영** 여섯 단계다. 어떤 모델로 작업하든 최종 판단은 Fable이 맡는다.

## 1. 범위 정리

1. `git status`, `git diff --stat`으로 바뀐 파일을 모은다. 인자가 있으면 그 범위로 좁힌다.
2. 프로젝트 CLAUDE.md가 가리키는 명세(예: `.docs/` 기능 절, 미결정사항, 기능정의서 원본)와 디자인 시안(Figma 파일, 기능 절의 Figma 링크)을 찾는다.
3. 이번 세션에서 사용자가 이미 내린 결정을 목록으로 만든다. 수집 에이전트가 이를 문제로 다시 올리지 않게 하는 용도다.
4. 위 내용을 스크래치패드의 `review-context.md` 하나에 적는다: 바뀐 파일 목록, 기능 ID와 명세 절 위치, Figma 파일 키와 노드, 사용자 결정 목록, 실행해 둔 테스트 결과.
   - 내 결론이나 의심 지점은 적지 않는다. 수집 에이전트는 코드와 명세를 직접 보고 판단한다.

## 2. 병렬 수집 (저렴한 모델)

관점마다 에이전트 하나, **한 메시지에서 동시에** 띄운다. 모델은 Fable보다 저렴한 것을 작업 난이도에 맞춰 고른다.

| 관점 | 모델 | 할 일 |
| --- | --- | --- |
| 주석 컨벤션 | sonnet | `comment-style` 스킬 로드 후 새로 쓰거나 고친 주석마다 "지우면 잃는 것"과 위반 규칙 보고 |
| 테스트 범위 | sonnet | 명세 `권한`, `실패` 항목마다 테스트가 있는지, 테스트가 정말 그 조건으로 실패할 수 있는지 |
| 명세 대조 | sonnet 또는 opus | 기능 절의 입력, 처리, 규칙, 실패, 출력과 구현 대조, 명세 근거 줄과 원본 정의서의 충돌 |
| 시안 대조 | opus | Figma에서 같은 기능의 화면(목록, 상세, 팝업, 모바일) 전부 찾아 표시 값, 필터, 버튼과 API 응답 대조 |
| 성능, 예외 | opus | 쿼리 수, N+1, 대량 행, 경계값, null, 동시성, 500이 날 입력. 가능하면 실제 실행으로 확인 |

- 수집 에이전트는 파일을 고치지 않는다. 코드를 실행해야 하면 `isolation: "worktree"`를 준다.
- 프롬프트에는 `review-context.md` 경로, 맡은 관점, 다른 관점은 보지 말라는 범위, 보고 형식을 넣는다.
- 보고 형식: 항목마다 `파일:줄`, 주장, 근거(인용하거나 실행한 결과), 심각도, 분류(`comment`, `test`, `code`, `api`, `spec-doc`, `business-rule`, `design`).

## 3. Fable 판단

- 작업 세션이 Fable이면 직접 판단한다. 아니면 `model: "fable"` 에이전트 하나를 띄워 수집 보고 전문과 `review-context.md` 경로를 넘긴다.
- Fable은 수집 보고를 가설로 다룬다. 항목마다 코드, 명세, 시안을 직접 열고 필요하면 tinker나 테스트로 재현한다.
  - 예: "삭제된 상품이면 500"이라는 보고가 실제 실행에서는 `product: null` 정상 응답이었다.
- 판정 결과는 네 묶음으로 돌려받는다.
  1. **자동 처리:** 분류가 `comment`, `test`인 확인된 문제. 고칠 파일, 줄, 바꿀 문구나 추가할 테스트 케이스까지 구체적으로
  2. **질문:** 그 밖의 확인된 문제와 결정이 필요한 것. 항목마다 독립된 질문 한 개, 선택지 2~4개, 추천안 표시
  3. **문제 아님:** 기각한 보고와 그 근거
  4. **검증 못 함:** 확인하지 못한 범위와 이유

## 4. 자동 수정 (묻지 않음)

- 사용자에게 판단 요약(자동 처리, 질문 예정, 문제 아님, 검증 못 함)을 짧게 알린 뒤 자동 처리 묶음을 바로 고친다.
- 주석은 `comment-style` 스킬을 먼저 로드한다.
- 테스트 실행 전 예상 개수를 말하고, 실행 후 개수와 통과 여부를 맞춰 본다.
- 주석, 테스트 수정은 사용자에게 확인을 묻지 않는다. 질문 묶음에 넣지 않는다.

## 5. 항목별 질문

- AskUserQuestion으로 **항목 하나에 질문 하나**를 쓴다. 여러 항목을 한 질문에 묶지 않는다.
- 한 번 호출에 최대 4개, 남으면 답을 받은 뒤 다음 묶음을 보낸다. 같은 분류끼리 묶어 보낸다.
- 질문마다 `[분류 n/N]`을 앞에 붙이고, 앞선 대화를 못 봐도 이해되게 무엇이 왜 문제인지 한두 문장으로 적는다.
- 답이 새 업무 규칙을 낳으면(예: "서버 자동 배정" 선택 후 배정 순서, 요청 형식) 구현 전에 그 세부를 다시 묻는다.

## 6. 반영과 보고

1. 승인된 항목을 구현하고 명세 문서(기능 절 처리, 규칙, 실패, 출력, 근거, 미결정사항)를 함께 고친다.
2. 새 동작마다 테스트를 추가하고, 관련 테스트와 전체 테스트를 예상 개수와 함께 실행한다.
3. 프로젝트 CLAUDE.md의 완료 기준을 따른다(미결 목록 유지, 칸반 갱신 제안은 승인 후 반영). 커밋은 요청이 있을 때만 한다.
4. 보고: 자동 수정한 것, 결정 반영한 것, 문서 변경, 테스트 결과, 미결 목록.
