# fable-review: 저렴한 수집, Fable 판단, 항목별 질문

입력: $ARGUMENTS (검토 범위나 추가 관점, 없으면 1단계 순서로 정함)

흐름은 **범위 정리 -> 병렬 수집 -> Fable 판단 -> 자동 수정 -> 항목별 질문 -> 반영** 여섯 단계다. 어떤 모델로 작업하든 최종 판단은 Fable이 맡는다.

## 1. 범위 정리

1. `git status`, `git diff --stat`으로 바뀐 파일을 모은다. 인자가 있으면 그 범위로 좁힌다. 인자가 없으면 아래 순서로 처음 있는 것을 범위로 삼는다.
   1. 커밋 안 된 변경
   2. 이번 세션에서 바꾼 파일
   3. 이번 대화에서 제안했지만 아직 적용하지 않은 계획. 계획이 고칠 파일을 바뀐 파일로 보고 아래 단계를 그대로 진행한다
   4. 위가 모두 없으면 최근 커밋 중 무엇을 볼지 AskUserQuestion으로 묻는다
2. 바뀐 파일을 종류로 나눈다: 실행되는 것(코드, 스크립트), 설정, 문서(마크다운, 스킬, 프롬프트).
3. 검토 기준을 있는 것만 모은다.

   | 기준 | 어디서 찾나 |
   | --- | --- |
   | 요청과 결정 | 이번 대화에서 사용자가 한 요청(요약하지 않고 그대로)과 이미 내린 결정 |
   | 프로젝트 규칙 | CLAUDE.md, rules |
   | 설명 문서 | README, 바뀐 파일을 설명하는 문서, 있으면 명세 |
   | 기존 관례 | 기존 테스트, 같은 종류의 주변 파일 |
   | 시안 | 있으면 Figma 파일과 노드 |

4. 위 내용을 스크래치패드의 `review-context.md` 하나에 적는다: 바뀐 파일 목록과 종류, 요청 원문, 사용자 결정 목록, 기준 문서 위치, 실행해 둔 테스트 결과.
   - 사용자 결정은 수집 에이전트가 문제로 다시 올리지 않게 하는 용도다.
   - 내 결론이나 의심 지점은 적지 않는다. 수집 에이전트는 변경과 기준을 직접 보고 판단한다.

## 2. 병렬 수집 (저렴한 모델)

"붙는 때"에 맞는 관점만 골라, 관점마다 에이전트 하나를 **한 메시지에서 동시에** 띄운다. 모델은 Fable보다 저렴한 것을 작업 난이도에 맞춰 고른다.

| 관점 | 모델 | 할 일 | 붙는 때 |
| --- | --- | --- | --- |
| 기준 대조 | sonnet 또는 opus | 요청, 결정, 프로젝트 규칙과 변경을 하나씩 대조. 빠진 것, 요청에 없는 변경, 기준끼리 어긋나는 곳. 명세가 있으면 그 절의 항목과도 대조 | 항상 |
| 영향 범위 | sonnet | 바뀐 이름, 경로, 단계 수, 설명을 가리키는 다른 곳(README, 설치 스크립트, 호출부, 머리말 설명과 본문)이 아직 맞는지 | 항상 |
| 주석 컨벤션 | sonnet | `comment-style` 스킬 로드 후 새로 쓰거나 고친 주석마다 "지우면 잃는 것"과 위반 규칙 보고 | 주석 줄이 새로 생기거나 바뀜 |
| 테스트 범위 | sonnet | 바뀐 동작과 코드의 실패 갈래마다 테스트가 있는지, 테스트가 정말 그 조건으로 실패할 수 있는지. 명세가 있으면 권한, 실패 항목도 | 실행되는 것이 바뀌고 프로젝트에 테스트가 있음 |
| 동작, 예외 | opus | 경계값, 빈 입력, null, 없는 파일, 다시 실행해도 안전한지, 동시성. 데이터를 다루면 쿼리 수와 대량 행. 가능하면 실제 실행으로 확인 | 실행되는 것이 바뀜 |
| 시안 대조 | opus | 시안에서 같은 기능의 화면(목록, 상세, 팝업, 모바일)을 전부 찾아 표시 값, 필터, 버튼과 구현 대조 | 시안이 있고 화면이나 화면용 응답이 바뀜 |

- 변경이 아주 작으면(파일 한두 개, 몇 줄) 수집을 건너뛰고 Fable이 직접 본다.
- 건너뛴 관점은 이유와 함께 6단계 보고에 적는다(예: 테스트 없음).
- 수집 에이전트는 파일을 고치지 않는다. 코드를 실행해야 하면 `isolation: "worktree"`를 준다.
- 프롬프트에는 `review-context.md` 경로, 맡은 관점, 다른 관점은 보지 말라는 범위, 보고 형식을 넣는다.
- 보고 형식: 항목마다 `파일:줄`, 주장, 근거(인용하거나 실행한 결과), 심각도, 분류(`comment`, `test`, `code`, `doc`, `decision`). `decision`은 고칠 방향이 여럿이라 사용자가 정해야 하는 것이다.

## 3. Fable 판단

- 작업 세션이 Fable이면 직접 판단한다. 아니면 `model: "fable"` 에이전트 하나를 띄워 수집 보고 전문과 `review-context.md` 경로를 넘긴다.
- Fable은 수집 보고를 가설로 다룬다. 항목마다 변경과 기준을 직접 열고, 필요하면 실제 실행이나 테스트로 재현한다. 문서는 가리키는 파일, 경로, 명령이 실제로 있는지 확인한다.
  - 예: "지워진 항목이면 오류가 난다"는 보고가 실제 실행에서는 정상 응답이었다.
- 판정 결과는 네 묶음으로 돌려받는다.
  1. **자동 처리:** 분류가 `comment`, `test`인 확인된 문제. 고칠 파일, 줄, 바꿀 문구나 추가할 테스트 케이스까지 구체적으로
  2. **질문:** 그 밖의 확인된 문제와 결정이 필요한 것. 항목마다 독립된 질문 한 개, 선택지 2~4개, 추천안 표시
  3. **문제 아님:** 기각한 보고와 그 근거
  4. **검증 못 함:** 확인하지 못한 범위와 이유

## 4. 자동 수정 (묻지 않음)

- 사용자에게 판단 요약(자동 처리, 질문 예정, 문제 아님, 검증 못 함)을 짧게 알린 뒤 자동 처리 묶음을 바로 고친다.
- 주석은 `comment-style` 스킬을 먼저 로드한다.
- 테스트 실행 전 예상 개수를 말하고, 실행 후 개수와 통과 여부를 맞춰 본다.
- 주석, 테스트 수정은 사용자에게 확인을 묻지 않는다. 질문 묶음에 넣지 않는다.

## 5. 항목별 질문

- AskUserQuestion으로 **항목 하나에 질문 하나**를 쓴다. 여러 항목을 한 질문에 묶지 않는다.
- 한 번 호출에 최대 4개, 남으면 답을 받은 뒤 다음 묶음을 보낸다. 같은 분류끼리 묶어 보낸다.
- 질문마다 `[분류 n/N]`을 앞에 붙이고, 앞선 대화를 못 봐도 이해되게 무엇이 왜 문제인지 한두 문장으로 적는다.
- 답이 새 규칙이나 세부 결정을 낳으면 반영하기 전에 그 세부를 다시 묻는다.

## 6. 반영과 보고

1. 승인된 항목을 반영하고, 바뀐 내용을 설명하는 문서(README, 명세 등)가 있으면 함께 고친다.
   - 범위가 아직 적용하지 않은 계획이면 질문에 대한 답을 적용 지시로 본다. 답을 반영한 계획을 끝까지 실행한다(계획에 든 렌더링, 재생성 같은 후속 작업 포함). 따로 다시 묻지 않는다.
2. 테스트가 있는 프로젝트면 새 동작마다 테스트를 추가하고, 관련 테스트와 전체 테스트를 예상 개수와 함께 실행한다. 없으면 확인 명령(실행, 문법 검사 등)을 돌린다.
3. 프로젝트 CLAUDE.md에 완료 기준이 있으면 따른다. 커밋은 요청이 있을 때만 한다.
4. 보고: 자동 수정한 것, 결정 반영한 것, 문서 변경, 테스트나 확인 결과, 건너뛴 관점, 미결 목록.
