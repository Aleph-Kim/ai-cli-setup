# fable-team: Fable 지시, 병렬 작업, Fable 검수

입력: $ARGUMENTS (할 작업, 없으면 이번 대화에서 남은 작업)

흐름은 **맥락 정리 -> Fable 지시서 -> 병렬 작업 -> 순서 작업 -> Fable 검수 -> 보고** 여섯 단계다. 비싼 모델(Fable)은 나누기와 검수만 하고, 실제 수정은 저렴한 모델이 동시에 한다. 메인 세션은 큰 파일을 직접 읽지 않고 지시서와 보고만 주고받아 대화 토큰을 아낀다.

- 에이전트는 다른 에이전트를 띄울 수 없다. 그래서 Fable은 지시서만 돌려주고, 작업 에이전트는 **메인 세션이** 띄운다.
- 작업이 작으면 이 스킬이 더 느리다. 서로 독립적인 작업이 2개 이상이고 고칠 파일이 3개 이상일 때만 쓴다. 아니면 사용자에게 그렇다고 말하고 직접 한다.
- 커밋과 푸시는 사용자가 요청할 때만 한다. 작업 에이전트에게는 늘 금지로 적는다.

## 1. 맥락 정리

스크래치패드에 `team-context.md` 하나를 쓴다. 작업 에이전트는 대화를 보지 못하므로 이 파일이 그들이 아는 전부다.

1. 원래 요청: 사용자가 한 말을 그대로 옮긴다(요약하지 않음).
2. 이미 정한 사용자 결정: 이번 대화와 프로젝트 문서(CLAUDE.md, 계획 문서, 요청 기록)에서 모은다. 다시 묻거나 되돌리면 안 되는 것.
3. 지켜야 할 규칙: 프로젝트 CLAUDE.md와 rules에서 이 작업에 걸리는 것(주석 스타일, 문서 말투, 금지 문자, 라이선스, 외부 호출 금지 등). 스킬을 먼저 로드해야 하는 규칙은 스킬 이름까지.
4. 관련 파일과 현재 상태: 경로, 이미 끝난 것, 남은 것. 파일 내용은 붙이지 않고 경로만.
5. 확인 방법: 테스트, 검증 스크립트, 빌드 명령과 기대 결과.
6. 공용 자원 주의: 임시 파일 위치(스크래치패드), 디스크 공간, 드라이브나 원격 저장소처럼 느린 위치, 다른 세션이 쓰는 서버.

## 2. Fable 지시서

- 메인 세션이 Fable이면 직접 쓴다. 아니면 `model: "fable"` 에이전트 하나를 띄워 `team-context.md` 경로를 넘기고 지시서만 돌려받는다(Fable은 파일을 고치지 않음).
- 이미 일을 하고 있던 Fable 에이전트를 지시서 역할로 바꿀 때는 "지금 고치던 파일만 저장하고 멈춘 뒤, 끝낸 것과 남은 일 지시서를 최종 보고로 돌려줘"라고 보낸다.

지시서 형식(지시서마다 전부 채움):

| 칸 | 내용 |
| --- | --- |
| id | A, B, C ... |
| 모델 | `sonnet`(정해진 수정, 문서 고치기, 형식 맞추기) 또는 `opus`(측정과 점검, 그림이나 화면을 직접 보고 판단, 문서끼리 교차 검토, 원인 찾기) |
| 담당 파일 | 이 지시서만 고칠 수 있는 파일(절대 경로) |
| 할 일 | 무엇을 어떤 기준으로. 사용자 결정 중 이 지시서에 걸리는 것을 다시 적음 |
| 확인 방법 | 끝났다고 말하기 전에 돌릴 명령이나 열어 볼 파일과 기대 결과 |
| 건드리면 안 되는 파일 | 다른 지시서 담당 파일과 결과물 원본 |
| 순서 | `동시` 또는 `뒤에`(어느 지시서가 끝난 뒤) |

나누는 규칙:
- **담당 파일이 겹치면 안 된다.** 두 지시서가 같은 파일을 고쳐야 하면 하나로 합치거나 한쪽은 보고만 하게 한다.
- 결과물을 통째로 다시 만드는 일(렌더링, 빌드, 전체 생성)은 하나의 `뒤에` 지시서로 모아 마지막에 한 번만 한다. 동시 지시서가 그 결과물을 읽는 동안 바뀌면 점검 값이 어긋난다.
- 다른 지시서의 결과를 기다려야 하는 칸(예: 검증 결과로 채우는 점검표 줄)은 "아직 확인 안 함"으로 두게 하고, 메인 세션이 마지막에 채운다.
- 고치지 말고 보고만 할 것(사용자 판단이 필요한 것, 다른 담당 파일의 문제)은 "보고만"이라고 적는다.

## 3. 병렬 작업

- `순서: 동시`인 지시서를 **한 메시지에서 동시에** 띄운다. `model`은 지시서 값 그대로. 일반 에이전트(`general-purpose`)를 쓴다.
- 프롬프트 = 공통 줄 + 지시서 전문 + `team-context.md` 경로. 공통 줄: 커밋과 푸시 금지, 새 프로그램 설치 금지, 담당 파일 밖은 고치지 않음, 임시 파일은 스크래치패드 안에만, 보고는 짧게(바꾼 파일, 확인 결과, 못 한 것, 보고만 할 것).
- 코드를 실행해 확인해야 하고 담당 파일이 같은 작업 트리를 공유하면 위험할 때는 `isolation: "worktree"`를 준다.
- 기다리는 동안 메인 세션은 지시서 파일을 직접 고치지 않는다. 작은 문제를 보고받으면 기록해 두고 4단계나 검수 뒤에 처리한다.
- 사용자가 진행을 물으면 에이전트 기록 파일을 열지 말고, 담당 파일의 수정 시각으로 어디까지 됐는지 알려 준다.

## 4. 순서 작업

- 동시 지시서가 모두 끝나면 `뒤에` 지시서를 띄우거나 메인 세션이 직접 한다(명령 몇 개면 직접).
- 동시 작업 중 보고된 "보고만" 항목 가운데 간단한 것(한두 줄 수정)은 이때 함께 고치고, 결과물을 다시 만들 일이 있으면 한 번에 모은다.

## 5. Fable 검수

- `model: "fable"` 에이전트 하나에 `team-context.md` 경로, 지시서 전문, 작업 보고 전문을 넘긴다(메인 세션이 Fable이면 직접).
- Fable은 보고를 믿지 않고 가설로 다룬다. 원래 요청과 사용자 결정 하나하나에 대해 실제 파일을 열고 확인 명령을 다시 돌려 판정한다.
- 판정은 네 묶음으로 돌려받는다.
  1. **통과:** 근거(파일:줄, 명령 결과)
  2. **고칠 것:** 2단계와 같은 형식의 새 지시서
  3. **사용자에게 물을 것:** 결정이 필요한 것. 항목마다 질문 하나와 선택지
  4. **확인 못 함:** 사람이 들어 보거나 봐야 하는 것 등, 이유와 함께
- 고칠 것이 있으면 3~5단계를 **한 번 더**만 돈다. 두 번째 검수에서도 남으면 더 돌리지 않고 남은 그대로 보고한다.

## 6. 보고

사용자에게 짧게, 표로:
- 지시서별 결과(모델, 담당, 끝남 여부)
- 바뀐 파일 목록(`git status --short`와 대조해 예상 밖 파일이 없는지)
- 검수 결과의 통과, 확인 못 함, 사용자에게 물을 것(AskUserQuestion으로 항목마다 하나)
- 기준에 못 미친 것은 지우지 않고 그대로

## 겪은 일

- 같은 파일을 두 에이전트가 고치는 것을 막으려고 담당 파일 칸이 생겼다. 지시서가 길어지는 이유는 작업 에이전트가 대화의 결정을 모르기 때문이고, 줄이지 않는다.
- 임시 스크립트 오류 하나가 수십 GB 파일을 만들어 디스크가 차자 클라우드 동기화 앱까지 멈춘 일이 있다. 반복문에서 표준 입력을 읽는 명령(ffmpeg 등)은 입력을 막아 두고(`-nostdin`), 큰 출력을 만드는 단계 뒤에는 남은 공간을 본다.
- 교차 검토 지시서(문서끼리, 문서와 스크립트 실제 동작이 어긋나는 곳 찾기)를 하나 넣으면 작업 지시서만으로는 못 찾는 문제가 나온다. 이 지시서는 고치지 않고 목록만 보고하게 한다.
