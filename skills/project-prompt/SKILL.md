# project-prompt — 프로젝트 세팅 프롬프트 생성기

주제: $ARGUMENTS

주제가 비어 있으면 무엇을 만들 프로젝트인지 먼저 묻는다.

## 0. 이 스킬의 결과물

**최종 산출물은 코드가 아니라 `.md` 파일 하나**다. 그 파일을 다른 세션이나 코딩 에이전트에 통째로 붙여넣으면 프로젝트 스캐폴딩이 나오는 수준이어야 한다. 이 세션에서 실제 구현을 시작하지 않는다.

흐름은 **질문 라운드 → 프롬프트 작성 → 파일 전달** 세 단계다.

## 1. 질문 라운드

주제만 보고 스택과 기능을 혼자 정하지 않는다. 하지만 매번 백지에서 묻지도 않는다. **추천안을 먼저 만들고 그것을 확인받는 방식**으로 간다. 사용자가 고르기만 하면 되게 만드는 것이 이 스킬의 핵심 가치다.

### 질문 도구

세션에 인터랙티브 질문 도구(`ask_user_input_v0` 등 선택지 버튼을 띄우는 도구)가 있으면 그것을 쓴다. 없으면 번호 붙인 객관식으로 텍스트에 적는다.

- **한 라운드에 질문 3개까지, 선택지는 항목당 2~4개.** 도구 제약이기도 하고, 그 이상은 사용자가 읽다 지친다.
- 라운드는 **최대 3번**. 3번 안에 못 좁힌 항목은 프롬프트에 물어보지 말고 합리적 기본값으로 채운 뒤 "이 부분은 이렇게 잡았습니다"라고 한 줄로 알린다.
- 답이 열려 있는 항목(스택 세부 버전, 외부 서비스 이름 등)은 선택지 마지막을 `직접 입력`으로 둔다.
- **이미 답이 나온 것은 묻지 않는다.** 사용자가 처음 문장에서 "Flutter로", "로그인 없이" 라고 밝혔으면 그 항목은 건너뛴다.
- 질문 도구를 호출하면 그 턴은 거기서 끝난다. 호출 뒤에 계속 쓰지 않는다.

### 라운드 1 — 스택과 프로젝트 성격

주제를 보고 **가장 적합한 스택 조합 하나를 추천안으로 만들어** 첫 선택지에 놓는다. 나머지 선택지는 현실적인 대안이다.

추천 기준:

| 주제 성격 | 1순위 추천 |
|---|---|
| 웹 서비스, 관리자 페이지, CRUD, 사내 도구 | PHP 8.3 / Laravel(최신 안정 버전) / MariaDB 11.8.2 |
| 모바일 앱(iOS·Android 동시) | Flutter |
| 브라우저에서 완결되는 단일 도구·시각화 | 백엔드 없는 단일 HTML |
| 배치·데이터 처리·스크립트 | Python |

표는 출발점이지 규칙이 아니다. 주제가 실시간 통신이나 대용량 스트리밍처럼 위 조합이 안 맞는 성격이면 맞는 것을 추천하고, **왜 그걸 골랐는지 한 줄로 밝힌다.**

이 라운드에서 확인할 것:
1. 스택 조합 (추천안 / 대안 / 직접 입력)
2. 프로젝트 범위 — 개인용 단일 사용자 / 여러 사용자 / 공개 서비스
3. 실행 환경 — 로컬 개발만 / 서버 배포까지 포함 (배포를 포함하면 산출물에 배포 절차가 들어간다)

### 라운드 2 — 기능과 데이터

라운드 1 답을 받은 뒤, **기능 목록을 먼저 초안으로 써서 보여주고** 거기에 대해 묻는다. "어떤 기능이 필요하세요?" 같은 백지 질문을 던지지 않는다.

확인할 것:
1. 인증 — 없음 / 환경변수 기반 단일 관리자 / 사용자 테이블 기반 회원가입
2. 초안 기능 목록 중 뺄 것·더할 것 (다중 선택)
3. 데이터 저장 형태 — DB 테이블 / 파일 / 외부 API 연동

인증 선택지 설명은 정확하게 적는다. "환경변수 기반 단일 관리자"는 `users` 테이블도 스타터 킷도 쓰지 않고 `.env` 의 해시 하나로 로그인하는 방식이라는 뜻이다.

### 라운드 2-B — 유형별 추가 확인 (해당될 때만)

주제에 아래 성격이 섞여 있으면 라운드 2 질문 세 개 중 하나를 이쪽으로 바꾼다. **일반 CRUD 질문보다 이 항목들이 프로젝트 난이도를 훨씬 크게 좌우한다.** 여기서 안 물으면 받는 쪽이 임의로 정하고, 그 임의값은 대개 틀린다.

| 성격 | 확인할 것 | 프롬프트에 추가되는 절 |
|---|---|---|
| 외부 API 연동 | 인증 키 필요 여부, 호출 한도, 증분 조회 기준 | `## 외부 API 계약` |
| 주기 실행·배치 | 실행 주기, 중복 실행 방지, 실패 시 처리 | `## 스케줄` |
| 알림 발송 (웹푸시·메일·메신저) | 구독 정보 저장 위치, 중복 알림 차단 기준 | `## 알림` |
| 파일 업로드 | 허용 형식·용량, 저장 위치 | 기능 절 안에 |
| 시간대·다국어 | 기준 시간대, 저장 시각의 형태 | 데이터 모델 절 안에 |

### 외부 API를 붙이는 프로젝트

- 엔드포인트 URL, 파라미터 이름, 응답 필드명은 **공식 문서에서 확인한 것만** 적는다. 필드명 하나가 틀리면 받는 쪽은 코드를 다 쓰고 실행한 뒤에야 안다.
- **호출 한도와 페이지네이션 방식을 반드시 적는다.** 이게 없으면 받는 쪽이 전체를 한 번에 긁는 코드를 쓰고, 실서비스에서 차단당한다.
- **증분 조회 기준을 명시한다.** 마지막 조회 시각을 어디에 저장하고 다음 호출에 어떤 파라미터로 넘기는지까지 적어야 한다. 이 한 문장이 없으면 매번 전량 조회하는 구현이 나온다.
- 확인 못 한 항목은 지어내지 말고 `> 확인 필요:` 로 남긴다. 받는 쪽이 문서를 보고 채우게 된다.

### 알림을 보내는 프로젝트

- **중복 차단 키를 반드시 정한다.** "무엇이 같으면 다시 보내지 않는가"를 한 줄로 못 쓰면 그 기능은 아직 설계되지 않은 것이다. 주기 실행과 알림이 만나면 중복 발송이 기본값이다.
- 웹푸시는 구독 객체 저장과 키 관리가 선행 조건이다. 이 준비물을 기능 절보다 앞에 적는다.
- 발송 실패를 어떻게 처리하는지(재시도 / 만료된 구독 삭제) 적는다.

### 라운드 3 — 디자인과 산출물 범위

1. 디자인 방향 — 미니멀 문서형 + 도트 폰트 프리셋 / 프레임워크 기본 스타일 / 별도 지정
   - 첫 번째를 고르면 `references/design-preset.md` 를 읽어 그 내용을 프롬프트의 디자인 절에 그대로 옮긴다.
2. 산출물 상세도 — 파일 단위 전체 코드 / 핵심 파일만 / 구조와 스펙만
3. 빠뜨린 게 있는지 자유 입력 한 번

## 2. 프롬프트 작성

### 항상 들어가는 제약 블록

아래는 사용자가 매번 요구하는 고정 규칙이다. 주제와 무관하게 `## 역할 및 제약` 에 넣는다. 스택이 Laravel이 아니면 해당 언어·프레임워크 이름으로 바꾼다.

```
- 확인되지 않은 해결책 제시 금지. 모르면 "확인 필요"라고 명시할 것
- 추측성 코드 금지, 검증된 API만 사용
- 여러 방식을 나열하지 말고 가장 확실한 방법 하나만 제시
- 설명은 최소화하고 파일 단위 전체 코드를 제공. 생략(`// ...`) 금지
- 단순 MVC 구조로만 작성한다. Service / Repository / Action / DTO 등 별도 레이어를 만들지 말 것
```

마지막 줄은 서버 프레임워크 프로젝트에만 넣는다. Flutter나 단일 HTML 프로젝트에는 해당 스택의 과잉 추상화 금지 문구로 바꾼다.

### 버전 사실은 지어내지 않는다 (가장 중요)

프롬프트를 받는 쪽은 거기 적힌 구조를 사실로 믿고 그대로 코드를 쓴다. 그래서 **틀린 버전 정보 한 줄이 프로젝트 전체를 망가뜨린다.**

- 프레임워크 **최신 안정 버전 번호는 반드시 검색해서 확인**한다. 기억으로 쓰지 않는다.
- 버전별 구조 주장(파일 경로, 클래스명, 등록 방식, 이름이 바뀐 미들웨어 등)은 공식 문서에서 확인한 것만 쓴다.
- 확인 못 했으면 **그 주장을 아예 빼고** 버전만 적는다. "아마 이럴 것"으로 채우지 않는다.
- 확인은 했지만 애매하면 프롬프트 안에 `> 확인 필요:` 로 남긴다. 받는 쪽이 검증하게 된다.

### 출력 템플릿

이 순서를 그대로 쓴다. 해당 없는 절은 통째로 뺀다(빈 절을 남기지 않는다).

```markdown
# 프롬프트 — <프로젝트 이름>

## 역할 및 제약
<스택·버전 한 줄> 환경의 개발자에게 답변한다.
<공식문서 URL>과 클린코드 기준으로만 작성한다.

- (위 고정 제약 블록)

## 만들 것
<3~5문장. 무엇을 위한 것이고 핵심 동작이 뭔지. 기능 나열이 아니라 성격 설명.>

## 기능 요구사항
### 1. <기능명>
- <동작 조건을 단정형으로>
### 2. <기능명>
...

## 데이터 모델
<테이블/필드 표 + 인덱스·제약. DB를 안 쓰면 저장 구조 설명으로 대체>

## 외부 API 계약   ← 라운드 2-B에서 해당될 때만
<엔드포인트, 인증, 호출 한도, 페이지네이션, 증분 조회 파라미터>

## 스케줄   ← 해당될 때만
<실행 주기, 중복 실행 방지, 실패 처리>

## 알림   ← 해당될 때만
<준비물, 발송 조건, 중복 차단 키, 실패 처리>

## 디자인 요구사항
<폰트, 색상 토큰, 레이아웃 규칙>

## 산출물
1. <파일 종류별 목록>
...
N. 설치 순서 (프로젝트 생성부터 실행까지)
```

### 쓰는 방식

- **단정형으로 쓴다.** "~하면 좋겠다"가 아니라 "~한다", "~하지 말 것".
- 입력 항목이 여러 개면 표로 쓴다. 문장으로 늘어놓지 않는다.
- 함정이 있는 부분은 이유를 한 줄 붙인다. 이유 없는 금지는 받는 쪽이 무시하거나 잘못 우회한다.
  - 예: `iframe에 sandbox="allow-scripts" 를 적용하고 allow-same-origin 은 넣지 않는다 (같이 넣으면 샌드박스가 무력화됨)`
- 라운드에서 확인하지 않은 항목을 슬쩍 채워 넣지 않는다. 기본값으로 채웠다면 채팅 답변에서 밝힌다.
- 분량은 주제 크기에 맞춘다. 작은 도구를 8000자로 부풀리지 않는다.

## 3. 파일 전달

`/mnt/user-data/outputs/<프로젝트-슬러그>-prompt.md` 로 저장하고 `present_files` 로 전달한다. 파일 내용을 채팅에 다시 출력하지 않는다.

채팅 답변은 짧게 남긴다:
- 기본값으로 채운 항목이 있으면 그것
- 검증하지 못해 `확인 필요`로 남긴 항목이 있으면 그것
- 없으면 한 줄로 끝낸다

## 4. 완료 전 점검

- 라운드 1에서 스택을 **추천안 형태로** 제시하고 확인받았는가 (백지 질문을 던지지 않았는가)
- 라운드 2에서 기능 초안을 먼저 보여주고 물었는가
- 프레임워크 버전 번호를 검색으로 확인했는가
- 확인 못 한 버전별 구조 주장을 프롬프트에 넣지 않았는가
- 라운드 2-B 표의 성격이 주제에 있는데 그냥 넘어가지 않았는가
- 외부 API를 쓴다면 호출 한도와 증분 조회 기준이 프롬프트에 있는가
- 알림을 보낸다면 중복 차단 키가 한 줄로 적혀 있는가
- 고정 제약 블록이 들어갔는가
- 산출물 절에 설치 순서가 마지막 항목으로 있는가
- 빈 절을 남기지 않았는가
- `.md` 파일로 저장하고 `present_files` 로 전달했는가 (본문을 채팅에 도배하지 않았는가)
