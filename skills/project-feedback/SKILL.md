# Project Feedback

완료된 작업물을 "정석 대비 무엇이 빠졌는가" 관점으로 진단한다. 칭찬·요약이 아니라 **지적**이 산출물이며, 결과는 md 파일로 저장한다.

## 호출

`/project-feedback [대상 경로]` 로만 실행된다. 경로가 함께 전달되면 그것을 점검 범위로 쓴다. 경로가 없고 범위가 불명확하면 진단 전에 한 번만 묻는다.

## 기술 스택 판별

1. 의존성 매니페스트와 **lock 파일**을 함께 확인한다 — `composer.json`/`composer.lock`, `package.json`/lock 파일, `build.gradle`, `pom.xml`, `requirements.txt`, `go.mod`, `Gemfile`/`Gemfile.lock` 등. 매니페스트는 버전 제약(예: `^10.10`)만 담고 있으므로 실제 설치 버전은 lock 파일에서 확정한다.
2. 수정안에는 확정한 버전에 실제로 존재하는 API만 쓴다. 버전을 확정하지 못하면 버전 의존 수정안은 쓰지 않는다.
3. 런타임·DB·인프라 확인 — 언어 버전 설정, `docker-compose.yml`, CI 워크플로, 마이그레이션 파일.
4. 리포트 상단에 판별한 스택을 명시한다.

프레임워크 관례 위반은 해당 버전 공식 문서에 근거가 있는 것만 지적한다. 확신이 없으면 `확인 필요`로 내린다.

## 아키텍처 판단 기준

현재 구조를 기준선으로 삼되, 코드에 근거가 있으면 새 계층 도입을 권고한다.

**흡수 우선.** 프레임워크 기본 수단으로 옮길 수 있는 로직(입력 검증, 반복되는 쿼리 조건, 응답 변환 등)은 먼저 그쪽으로 지적한다. 새 계층은 그 뒤에도 남는 비즈니스 로직에만 권고한다.

**새 계층 권고 조건** — 아래 중 하나 이상이 코드에서 확인될 때만:

- 같은 비즈니스 로직이 2곳 이상에 중복
- 한 진입점 메서드에 검증 이후의 다중 쓰기·외부 연동·후처리가 함께 들어 있음
- 같은 로직을 HTTP 외 진입점(콘솔 커맨드, 큐 작업, 스케줄러)에서도 써야 함

**권고 시 필수 기재:**

- 계층명과 역할 한 줄
- 옮길 코드의 `파일:라인`
- 적용 범위 규칙 — 어떤 로직을 이 계층에 두고 어떤 로직은 두지 않는지. 이 규칙이 없으면 일부 파일에만 계층이 섞여 구조가 오히려 나빠진다.

새 계층은 구체 클래스로 제안한다. 구현체가 하나뿐인 인터페이스나 위임만 하는 래퍼는 권고하지 않는다.

**이미 계층이 있는 경우:** 규칙이 일관되게 지켜졌는지 본다. 일부에만 적용된 계층은 실제 로직을 담고 있으면 전면 적용, 위임만 하면 제거로 판정한다.

## 핵심 원칙

1. **근거 없는 지적 금지.** 모든 항목에 실제로 읽은 코드의 `파일경로:라인`(확장자 포함 실제 경로)을 단다. 읽지 않은 파일은 지적하지 않는다.
2. **판정 불가는 확인 필요로.** 인덱스 존재 여부, 실제 트래픽, 운영 로그 설정처럼 코드만으로 판정할 수 없는 것은 단정하지 말고 `확인 필요`로 내린다.
3. **문제가 없으면 양호.** 분량을 채우려고 억지 항목을 만들지 않는다.
4. **수정안은 검증된 방법 하나만.** 대안을 나열하지 않는다.
5. **과잉 설계 권고 금지.** 인터페이스 추출, 이벤트 버스, 추상 클래스는 실제 구현체가 2개 이상이거나 재사용 요구가 코드에 있을 때만 권고한다. 새 계층은 "아키텍처 판단 기준"을 따른다.

| 주의 | 지금은 동작하지만 데이터·트래픽 증가나 장애 시 문제가 됨 | N+1, 실패 지점 로그 부재, 페이지네이션 부재 |
| 제안 | 동작에 영향 없는 구조·가독성·컨벤션 | 계층 도입, 타입 선언 누락, 중복 코드 |
| 확인 필요 | 코드만으로 판정 불가 | 인덱스 실재 여부, 운영 설정 |

## 진단 절차

1. 범위 확정
2. 스택 판별
3. 구조 파악 — 진입점(라우팅/엔드포인트 정의), 핵심 도메인 파일, 스키마 정의, 설정 파일로 전체 그림을 잡는다.
4. 카테고리별 스캔 — 체크리스트 순서대로 확인한다. `grep`으로 후보를 찾되 판정은 해당 코드를 직접 읽고 내린다.
5. 등급 분류
6. 리포트 저장

범위가 커서 전부 읽지 못하면 진입점과 쓰기 작업 경로를 우선 읽고, 읽지 못한 경로는 리포트의 `미점검 범위`에 적는다. 전체를 본 것처럼 쓰지 않는다.

## 점검 체크리스트

언어·프레임워크에 무관한 공통 항목이다. 판별한 스택의 관용 표현으로 바꿔 적용한다.

### A. 로깅 / 관측성

- 예외를 잡고 로그를 남기지 않는 코드
- 외부 API 호출, 결제, 파일 업로드, 비동기 작업 등 실패 추적이 필요한 지점의 로그 부재
- 로그 레벨 오용 (정상 흐름을 error로, 실제 장애를 info로)
- 로그에 비밀번호·토큰·개인정보 원문 노출
- 식별자 없는 로그 메시지 (어떤 요청·엔티티인지 추적 불가)

### B. 쿼리 / 성능

- N+1: 반복문 내부의 연관 데이터 접근, 즉시 로딩(eager loading) 부재
- 반복문 안의 쿼리 실행, 반복문 안의 개별 저장
- 대량 처리 시 스트리밍·청크 미사용으로 인한 메모리 위험
- 존재 확인에 전체 카운트 사용
- 불필요한 전체 컬럼 조회, 페이지네이션 부재
- 조건·정렬·조인 대상 컬럼의 인덱스 정의가 스키마에 있는지 대조
- 매 요청 재계산되는 정적 데이터의 캐시 부재
- 병렬 처리 가능한 외부 호출의 순차 실행

### C. 구조

- 구현체가 하나뿐인 인터페이스, 위임만 하는 래퍼 클래스
- 한 곳에서만 호출되는 유틸·믹스인·추상 클래스
- 일부에만 적용된 계층 (판정은 "아키텍처 판단 기준")
- 지나치게 긴 함수, 진입점(컨트롤러/핸들러)에 직접 들어간 도메인 로직·쿼리 (권고는 "아키텍처 판단 기준")
- 복붙 중복 코드

### D. 프레임워크 관례

- 입력 검증 위치·방식의 불일치, 검증 누락
- 설정값을 환경변수에서 직접 읽는 등 프레임워크 설정 체계 우회
- 다중 쓰기 작업의 트랜잭션 부재
- 내부 엔티티를 응답으로 직접 노출, 응답 포맷 불일치
- 무거운 작업의 동기 처리 (메일 발송, 외부 API, 이미지 처리 등)

### E. 데이터 / 스키마

- 외래키 제약 누락, 삭제 정책 미정의
- 부적절한 컬럼 타입 (금액에 부동소수점, 짧은 값에 대용량 타입)
- 의미 없는 nullable 남용
- 마이그레이션 롤백 불가
- 소프트 삭제 필요 여부와 실제 구현 불일치

### F. 예외 / 에러 처리

- 빈 catch, 광범위한 예외 포획으로 원인 유실
- 상태 코드 오용 (실패를 성공으로 반환)
- 사용자에게 내부 예외 메시지 그대로 노출
- 실패 시 롤백되지 않는 부분 커밋

### G. 컨벤션 / 코드 품질

- 해당 언어의 표준 스타일 가이드 위반, 네이밍 규칙 불일치
- 타입 선언이 가능한 언어인데 파라미터·반환 타입 누락
- 미사용 import, 죽은 코드, 주석 처리된 코드 블록
- 매직 넘버·하드코딩된 URL·경로
- 같은 일을 하는데 파일마다 방식이 다른 혼재된 스타일
- 린터·포매터 설정이 있는데 지켜지지 않은 코드

### H. 설정 / 배포

- 환경변수 예시 파일 누락 또는 실제 키와 불일치
- 테스트 부재 — 최소한 핵심 비즈니스 로직에 대한 테스트 유무
- 빌드·배포 스크립트와 실제 실행 환경 불일치

### I. 보안

- 인증·인가 처리 부재
- 사용자 입력을 문자열로 결합한 원시 쿼리 (파라미터 바인딩 미사용)
- 이스케이프 없이 출력되는 사용자 입력
- 파일 업로드의 확장자·MIME·크기 검증 부재
- CSRF 보호에서 제외된 경로의 타당성
- 대량 할당(mass assignment) 등 프레임워크 기본 보호 장치 미설정
- 저장소에 커밋된 비밀값

## 리포트 저장

1. `date +%F` 로 오늘 날짜를 얻는다.
2. 프로젝트 루트 기준 `docs/feedback/<YYYY-MM-DD>-<대상명>.md` 로 저장한다. 디렉터리가 없으면 만든다. 대상명은 kebab-case로 쓴다. 같은 이름의 파일이 있으면 덮어쓰지 않고 `-2`, `-3`을 붙인다.
3. 저장만 한다. `git add`·커밋은 하지 않는다.
4. 대화창에는 리포트 본문을 출력하지 않는다. 저장 경로와 `치명 N · 주의 N · 제안 N · 확인 필요 N` 한 줄만 출력한다.
