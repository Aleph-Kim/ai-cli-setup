# eli5 — 단계별 재생기 explainer

주제: $ARGUMENTS

주제가 비어 있으면 무엇을 설명할지 먼저 묻는다.

## 0. 시작 전 확인 (건너뛰지 않는다)

만들기 전에 `AskFollowupQuestion`(또는 `ask_question`) 도구를 호출해 사용자에게 필요한 옵션을 선택받는다. 사용자가 텍스트를 직접 입력하지 않고 버튼 클릭으로 선택할 수 있도록 구성한다. 답이 오면 그때 만든다.

### 0-1. 단일 주제인 경우
- 곧바로 **모드 확인(개념 모드 vs 구현 모드)** 질문 1회만 호출한다.
- 주제의 성격(개념·원리 중심 vs 실전 코드·구현 중심)을 분석하여 더 적합한 모드에 `(Recommended)`를 접두어로 붙이고 첫 번째 옵션에 배치한다.

### 0-2. 다중 주제인 경우 (반드시 2단계 순차 질문)
ARGUMENTS로 넘겨받은 주제가 여러 개(예: 쉼표 등으로 나열된 2개 이상의 주제)인 경우, **절대로 파일 구성과 모드를 한 번의 도구 호출에 합쳐서 묻지 않고 반드시 2단계로 나누어 순차 진행**한다.

1. **1단계 (파일 구성 방식 확인)**:
   - 파일 구성 방식(단일 통합 vs 개별 파일)만 먼저 단독으로 질문하고 사용자 응답을 대기한다. (모드 질문을 미리 섞지 않는다)
   - **단일 파일 (통합)**: 여러 주제 간의 관계, 비교, 연계 흐름을 하나의 아티팩트로 통합 작성
   - **여러 개의 파일 (개별)**: 각 주제마다 독립적인 아티팩트/파일을 개별 작성
   - 주제 간 연관성을 고려해 더 자연스러운 쪽에 `(Recommended)`를 접두어로 붙인다. 사용자가 처음부터 "하나로 합쳐서", "각각 따로" 처럼 파일 구성 방식을 명시했다면 1단계를 건너뛰고 바로 2단계로 간다.

2. **2단계 (모드 확인 — 1단계 사용자 응답 수신 후 분기)**:
   - **단일 파일(통합) 선택 시**: 전체 통합 내용을 아우르는 모드 **1개**를 질문한다.
   - **여러 개의 파일(개별) 선택 시**: 분리되는 **각 주제/개념마다 `AskFollowupQuestion`(또는 `ask_question`) 도구를 호출해 어떤 모드로 만들지 개별 질문(N개)으로 각각 확인**한다. (예: [1/2] Livewire의 모드 선택, [2/2] Turbo의 모드 선택)
   - 각 주제의 성격에 맞춰 더 적합한 모드에 `(Recommended)`를 붙인다.

> **주의 (Anti-pattern)**: 다중 주제일 때 파일 구성 방식이 확정되지 않은 상태에서 모드를 임의로 단일 공통 질문 1개로 축소하여 한 번에 물어보는 것은 엄격히 금지된다.

### 0-3. 모드별 성격
- **개념 모드**: 이게 뭐고 왜 필요한지, 구조와 동작 원리가 어떻게 생겼는지 (원리, 아키텍처, 이론, 과학/일상 주제 추천)
- **구현 모드**: 실제로 만들 때 어떤 순서로 무슨 코드를 작성하는지 (기능 개발, 라이브러리 연동, 셋업 순서 추천)

두 모드는 껍데기(정의 + 다이어그램 + phase + 재생 컨트롤)를 공유하고, 각 단계에 채우는 내용만 다르다.

## 1. 만드는 방법 — 셸을 다시 쓰지 않는다

HTML 전체를 새로 작성하지 않는다. CSS, 재생 컨트롤, dot indicator, 렌더 함수, 반응형 레이아웃은 `assets/shell.html`에 완성되어 있고 주제가 바뀌어도 동일하다. **주제마다 새로 만드는 것은 정의 블록, SVG 다이어그램, STEPS 배열 셋(+ 검증된 링크가 있으면 참고 링크 블록)뿐이다.**

각 문서마다 고유한 **영문 kebab-case 슬러그**(예: `hexagonal-architecture`, `vue-reactivity-system`, `oauth2-flow`)를 부여하여 중간 산출물과 최종 문서를 격리한다.

```bash
# 1) 슬러그 결정 및 격리 디렉토리 생성 (예: slug = "hexagonal-architecture")
mkdir -p /tmp/eli5-build/<slug>

# 2) /tmp/eli5-build/<slug>/ 안에 definition.html, diagram.svg, steps.js 세 파일 작성
#    (검증된 참고 링크가 1개 이상이면 links.html 도 작성 — 10절 참조, URL 할루시네이션 방지 규칙 필수)

# 3) 셸에 주입 (--accent 는 선택 사항. 미지정 시 주제 키워드 기반으로 최적 색상이 자동 선택됨)
python3 <스킬경로>/scripts/build.py \
  --slug       "<slug>" \
  --topic      "헥사고날 아키텍처" \
  --mode       "개념 모드" \
  --accent     "#d97706"
# 결과물: /tmp/eli5-build/<slug>.html 자동 생성
```

- **디렉토리 격리**: 중간 파일들은 `/tmp/eli5-build/<slug>/` 디렉토리에 두어 여러 문서를 작업할 때 서로 덮어쓰지 않는다.
- **색상 테마 & 대분류**: 주제 성격에 맞는 대표 색상 1개를 `--accent`로 넘기거나, 생략하면 `build.py`가 도메인 키워드로 자동 배정한다. 개발 도메인: 보안 `#4f46e5`, 인공지능/머신러닝 `#db2777`, 데이터베이스 `#059669`, 인프라/DevOps `#0891b2`, 소프트웨어 아키텍처 `#d97706`, 웹/프론트엔드 `#7c3aed`, 네트워크/통신 `#2563eb`, 컴퓨터 사이언스(알고리즘·자료구조 `#0d9488` / 저수준·OS·임베디드 `#475569` / 테스트·디버깅 `#e11d48`). 비개발 도메인: 자연과학 `#16a34a`·`#0284c7`, 경제/금융 `#b45309`, 의학/생명 `#be123c`, 인문/사회 `#8b5cf6`. `build.py`는 매칭된 **상위 대분류**도 함께 출력하며(예: `상위 대분류: 컴퓨터 사이언스`), 이 이름은 `docs-upload` 스킬의 카테고리 체계와 일치한다 — 분류표 원본은 `scripts/build.py`의 `DEV_DOMAIN_RULES`/`GENERAL_DOMAIN_RULES`이고, eli5 직후 업로드 시 출력된 대분류를 그대로 `--category`로 넘긴다.

셸을 열어 읽거나 내용을 다시 출력할 필요가 없다. 마커와 CSS 클래스는 아래에 다 적혀 있다. 셸을 고쳐야 할 만큼 구조가 안 맞는 주제라면, 고치기 전에 사용자에게 먼저 말한다.

## 2. 전달 및 실행

빌드 결과는 `/tmp/eli5-build/` 에만 두고, 사용자 작업 디렉토리에 임의의 HTML 파일을 남기지 않는다. 각 문서는 고유한 슬러그(`<slug>.html`)를 가지므로 이전 결과물이 덮어써지지 않고 병렬로 보존된다.

### 2-1. 단일 파일인 경우: 브라우저 즉시 오픈
- 빌드가 완료되면 터미널 명령(`open /tmp/eli5-build/<slug>.html`)을 즉시 실행하여 사용자의 기본 브라우저에서 완성된 인터랙티브 HTML 문서가 바로 열리도록 한다.
- 별도의 중간 마크다운 생성 없이 브라우저 오픈 완료 사실과 로컬 파일 링크(`[<slug>.html](file:///tmp/eli5-build/<slug>.html)`)를 간결하게 안내한다.

### 2-2. 다중 파일(개별 파일)인 경우: 통합 요약 마크다운(.md) 아티팩트 제공
주제가 여러 개여서 독립된 여러 HTML 파일로 생성한 경우, 각 문서별 고유 슬러그(`<slug1>.html`, `<slug2>.html` ...)로 생성하고 다음을 포함하는 **통합 마크다운(`.md`) 아티팩트를 작성하여 제공**한다:
1. **로컬 웹 서버 가동**: 백그라운드 웹 서버(`python3 -m http.server <port> --directory /tmp/eli5-build`)를 가동하여 브라우저에서 즉시 열리는 `http://localhost:<port>/<slug>.html` 1-클릭 실행 링크 및 `file://` 직접 링크 제공
2. **전체 주제 요약 맵**: 주제, 슬러그, 분류, 핵심 가치, 테마 색상 표
3. **브라우저 즉시 열기 링크 테이블**: 통합 대시보드(`/`) 및 각 개념별 브라우저 직접 실행 링크
4. **주제별 핵심 요약 블록**: 한 줄 정의, 핵심 규칙, 해결하려는 문제, 분석/변환 파이프라인 텍스트 다이어그램, 단계별 핵심 요약, 참고 링크(해당 HTML에 참고 링크 섹션이 있으면 그 목록을 텍스트로 미러링 — 없으면 생략)

### 2-3. 장식용 이모지 및 AI 아이콘 금지
생성하는 마크다운(.md) 아티팩트 및 설명 출력에는 `🚀`, `🌟`, `👉`, `📌`, `💡`, `📐`, `🔄`, `📝` 등 불필요한 AI 클리셰 장식용 이모지/아이콘을 일체 넣지 않는다. 깔끔하고 가독성 높은 표준 엔지니어링 문서 스타일을 유지한다.

## 3. 정의 블록 (definition.html)

과정만 보여주고 정의를 빠뜨리면 "결국 이게 뭔데?"가 남는다. 정의 블록은 다이어그램 위에 놓여 단계와 무관하게 같은 내용을 유지한다. **단계별 설명이 아니라, 사용자가 물어본 개념 자체의 정의다.**

두 층으로 쓴다. 한 줄 정의는 항상 보이고, 나머지는 접기 버튼으로 여닫는다(기본 펼침).

```html
<p class="one">비즈니스 로직을 가운데 두고, 바깥 세상(DB·웹·외부 API)과 닿는 지점을 전부 인터페이스로 밀어낸 구조.</p>
<div class="more">
  <dl>
    <dt>핵심 규칙</dt>
    <dd>의존성이 항상 바깥에서 안으로만 향한다. 코어는 자기가 어떤 프레임워크 위에서 도는지 모른다.</dd>
    <dt>해결하려는 문제</dt>
    <dd>DB나 프레임워크를 바꾸면 비즈니스 규칙까지 뜯어고쳐야 하는 상황.</dd>
    <dt>언제 과한가</dt>
    <dd>요청이 그대로 테이블 한 줄이 되는 CRUD. 갈아끼울 일이 없으면 파일만 늘어난다.</dd>
  </dl>
</div>
```

위 예시가 목표 수준이다. 한 줄 정의는 그 주제를 처음 듣는 사람이 읽고 정체를 잡을 수 있어야 하고, `핵심 규칙`은 그 개념을 한 문장으로 지탱하는 원리를 짚어야 한다. 둘 다 추상적인 수식어("유연한", "확장 가능한")로 때우지 않는다.

- `<p class="one">` 은 필수. **한 문장, 2줄 이내.** "~에 대해 알아봅니다" 처럼 정의를 미루는 문장은 금지.
- `<dl>` 은 **항목 3개**, `핵심 규칙`을 첫 항목으로 고정한다. 나머지 둘은 모드에 따라 정한다.
  - 개념 모드: `핵심 규칙` / `해결하려는 문제` / `언제 과한가`
  - 구현 모드: `핵심 규칙` / `무엇을 만드는가` / `전제 조건`
  - 각 `<dd>` 는 한두 문장.
- **개별 구성 요소의 정의는 여기 넣지 않는다.** "포트란 무엇인가"는 그것을 다루는 단계가 맡는다. 정의 블록은 개념 전체를 한 덩어리로 설명하는 자리이고, 단계는 그 안의 요소를 하나씩 푸는 자리다. 이 경계를 지켜야 두 층이 각자 값을 한다.
- 정의 + 다이어그램 + 리모컨이 첫 화면을 다 먹으면 단계가 안 보인다. `<dd>` 가 세 문장 이상이면 줄인다. 사용자는 접기 버튼으로 한 줄 정의만 남길 수 있다.

## 4. 다이어그램 (diagram.svg)

다이어그램 생성 시 **`diagram-design` 스킬**(`skills/diagram-design/`)의 39개 비주얼 레이아웃과 디자인 원칙을 적용하여 SVG를 작성한다.

### 4-1. 배치 형태를 먼저 정한다

SVG를 쓰기 전에 `diagram-design` 분류를 바탕으로 형태를 고르고, 왜 그 형태인지 스스로 확인한다. **가로 일렬은 "A 다음 B 다음 C" 순서가 실제로 존재하는 주제에만 쓴다.** 아키텍처·패턴·계층·의존성 방향이 주제라면 가로 파이프라인은 틀린 그림이다. 그림이 구조를 왜곡하면 설명 전체가 잘못 전달된다.

| 주제 성격 | 형태 | diagram-design 레퍼런스 | 예 |
|---|---|---|---|
| 시간 순서가 있는 흐름 | 가로 파이프라인 | `type-process.md` | 웹 푸시, OAuth, 요청/응답 |
| 단계별 변환 및 큐 경유 | 데이터 흐름 | `type-data-flow.md` | ETL 파이프라인, 이벤트 스트리밍 |
| 위아래 계층, 의존성이 한 방향 | 계층 스택 | `type-layers.md` | 레이어드 아키텍처, OSI, TCP/IP |
| 안과 밖, 중심이 바깥을 모름 | 중심 + 둘레 | `type-architecture.md` | 헥사고날, 클린 아키텍처, DDD |
| 상태와 전이 조건 | 상태 머신 | `type-state.md` | 결제 상태, 작업 생명주기 |
| 순환 주기 및 피드백 | 루프 / 플라이휠 | `type-loop.md` | 이벤트 루프, 캐시 갱신 주기 |
| 부모-자식 분해 관계 | 계층 트리 | `type-tree.md` | DOM/AST 트리, 컴포넌트 구조 |
| 서로 참조하는 관계망 | 관계망 / ERD | `type-er.md`, `type-dependency.md` | 마이크로서비스, DB ERD |

### 4-2. 중심 + 둘레 배치 좌표 (헥사고날·클린 아키텍처)

육각형 꼭짓점은 중심 `(cx, cy)`, 반지름 `r` 로 계산한다. `k = 0..5` 에 대해 `x = cx + r·cos(60k°)`, `y = cy + r·sin(60k°)`.

`cx=400, cy=230, r=150` 이면 `550,230  475,360  325,360  250,230  325,100  475,100`.

- 중앙 육각형 = 도메인. 안쪽에 도메인 요소를 배치한다.
- 포트는 **육각형 변 위에** 배치한다. 왼쪽 변에 인바운드(driving) 포트, 오른쪽 변에 아웃바운드(driven) 포트. 라벨이 완전히 들어가도록 박스 너비를 충분히 확보(90~110px 이상)하거나 라벨을 박스 바깥에 둔다.
- 어댑터는 육각형 **바깥** 좌우에 둔다. 왼쪽에 웹 컨트롤러·CLI, 오른쪽에 DB·외부 API.
- 화살표는 **항상 바깥 → 안쪽** 또는 **도메인 → 포트**로 그린다. 의존성 방향이 그림에서 보여야 한다.
- 좌우 어댑터가 여러 개면 세로로 쌓고, 육각형과 24px 이상 띄운다.

### 4-3. 공통 규칙 및 diagram-design 스타일 적용

`<svg viewBox="...">` 하나. `width`/`height` 속성을 넣지 않는다 (셸이 `width:100%;height:auto` 로 처리).

```svg
<defs>
  <!-- diagram-design 날렵한 8:5 에디토리얼 마커 -->
  <marker id="arrow" markerWidth="8" markerHeight="6" refX="7" refY="3" orient="auto">
    <polygon points="0 0.5, 8 3, 0 5.5" fill="context-stroke"/>
  </marker>
</defs>

<!-- 1. 화살표(edge): 노드보다 먼저 선언, 직각 라운드 엘보우(r=8) 또는 직선, 고대비 선색 -->
<g data-edge="web-port-in">
  <path d="M 150,230 H 212 Q 220,230 220,230 H 246" fill="none" stroke="#64748b" stroke-width="1.5" marker-end="url(#arrow)"/>
  <text x="198" y="222" text-anchor="middle" font-size="11" font-weight="500" fill="#475569">호출</text>
</g>

<!-- 2. 노드(node): 불투명 배경(fill="#ffffff")으로 선 침범 방지 -->
<g data-node="domain">
  <polygon points="550,230 475,360 325,360 250,230 325,100 475,100"
           fill="#ffffff" stroke="#cbd5e1" stroke-width="1.5"/>
  <text x="400" y="235" text-anchor="middle" font-size="13" font-weight="600" fill="#111418">도메인</text>
</g>
```

- **동적 하이라이트 원칙**: 노드는 `<g data-node="id">`, 화살표는 `<g data-edge="id">` 로 감싼다. 하이라이트는 셸 CSS의 `.dim { opacity: .18 }`이 처리하므로 SVG 내부 도형에 강제 선색이나 두께를 덮어쓰지 않고 Diagram Design의 고유 미학을 보존한다.
- **캔버스 배경**: Diagram Design 기본 표준에 따라 단색 종이 배경(`<rect width="100%" height="100%" fill="#f5f5f5" rx="8"/>`)을 사용하여 깔끔하고 정돈된 화면을 유지한다.
- **LEGEND(범례) 섹션 생략**: 다이어그램 하단에 별도의 LEGEND 박스를 두지 않는다. 각 컴포넌트의 역할과 의미는 노드 라벨/칩 뱃지 및 단계(Step) 카드의 상세 설명으로 온전히 전달하여 캔버스를 콤팩트하게 유지한다.
- **diagram-design 커넥터 규칙**:
  - 8:5 비율의 날렵한 에디토리얼 다트 마커(`points="0 0, 8 3, 0 6"`) 사용.
  - 축이 어긋난 노드 간 연결 시 사선(slanted line) 대신 직각 라운드 엘보우(`r=8`, `<path>`) 사용.
  - 화살표 라벨은 선 위에 `#f5f5f5` 마스킹 사각형을 깔고 Geist Mono로 중앙 배치.
- **박스 배경 숫자 워터마크 금지**: 노드 박스 배경에 장식용으로 흐릿하게 깔리는 거대한 인덱스 숫자(예: `01`, `02`, `03` 등 opacity 0.05~0.15 텍스트)를 절대 넣지 않는다. 시각적 노이즈를 유발하고 내부 텍스트 가독성을 저해한다. 순서나 인덱스가 필요하다면 작은 칩 뱃지(Eyebrow badge)에 깔끔하게 표기한다.
- **불필요한 영어 사용 지양 (한국어 우선 원칙)**: 표준 프로토콜/약어(HTTP, TCP, IP, API, CLI 등)나 고유명사를 제외하고, 장식용 영문 대문자(예: `ABSTRACTION`, `PHYSICAL`, `INBOUND`, `OUTBOUND` 등)의 남발을 금지한다. 노드 라벨, 축(axis), 관계 설명, 뱃지 등은 직관적이고 자연스러운 한국어(예: "상위 계층", "하위 계층", "인바운드 포트", "호출", "의존" 등)를 우선 사용한다.
- **사이징 및 텍스트 공식 (박스 텍스트 넘침 방지)**:
  - 노드 폭 = 가장 긴 줄 너비 + 좌우 여백 최소 24px (한글 1자 ≈ 글자크기 × 1.0, 영문 1자 ≈ 글자크기 × 0.6).
  - 노드 간 최소 간격 확보 (라벨 있는 구간 60~80px).
- **반응형 뷰포트**: 다이어그램 컨테이너(`.diagram`)는 셸 기본값으로 `width:100%;height:auto`를 쓴다 — 폭 100%를 채우는 것 자체는 문제가 아니다. 문제는 viewBox 세로/가로 비율이 높은(높이가 있는) 다이어그램이 폭 100%로 늘어나면 렌더링 높이도 비례해서 커져 하단 단계 설명이 화면 밖으로 밀려나는 것. **viewBox 높이/폭 비율이 대략 0.35 이상이면** `.diagram svg`에 그 문서에서만 `max-width`(렌더링 높이가 420px 안팎이 되도록 `420 ÷ (높이/폭 비율)`로 계산, block + `margin:0 auto`로 가운데 정렬)를 추가한다. 비율이 낮아 납작한 다이어그램(예: 940×250)은 폭 100%로도 렌더링 높이가 작으므로 그대로 둔다. 이 판단은 문서마다 다르므로 셸 전체 기본값을 바꾸지 않고 해당 문서의 `<style>`에서만 오버라이드한다. 하단 드래그 핸들로 필요 시 높이를 수동 조절할 수 있다.

## 5. steps.js 형식

`[` 로 시작하는 JS 배열 리터럴 하나만 담는다. 변수 선언이나 세미콜론을 붙이지 않는다.

```js
[
  {
    phase: '핵심 구조',
    title: '포트는 도메인이 요구하는 계약이다',
    summary: '도메인이 "이런 게 필요해"라고 선언만 하고, 누가 해줄지는 모른다.',
    where: '포트',
    lang: 'php',
    file: '',
    code: `interface OrderRepository
{
    public function findById(OrderId $id): ?Order;
}`,
    resultLabel: '이게 있을 때 / 없을 때',
    result: `<div class="mock">DB를 바꿀 때 고칠 파일 — 있을 때 1개 / 없을 때 47개</div>`,
    nodes: ['port-out'],
    edges: ['domain-port']
  }
]
```

- `code`, `lang`, `file`, `result` 는 비워도 된다. 빈 값이면 셸이 해당 칸을 통째로 생략한다. 채울 게 없으면 빈 문자열로 두고 억지로 만들지 않는다.
- `code` 는 백틱 문자열이므로 내부의 백틱과 `${` 는 이스케이프한다. HTML 특수문자는 셸이 자동 이스케이프하므로 그대로 쓴다.
- `result` 는 HTML 그대로 삽입된다. 아래 셸 제공 클래스를 쓴다.
- `nodes` / `edges` 는 SVG의 `data-node` / `data-edge` 값과 정확히 일치해야 한다. 둘 다 비우면 다이어그램 전체가 밝게 표시된다.
- `where` 는 다이어그램 활성 노드와 일치시킨다.

### 셸이 제공하는 목업 클래스

바깥은 `<div class="mock">`. 그 안에서:

- 테이블(DB 행): `<table><tr><th>컬럼</th></tr><tr><td>값</td></tr></table>`
- 터미널: `<div class="term">$ php artisan migrate<br>INFO Migrating.</div>`
- 변화 없음: `<span class="none">화면 변화 없음 — 서버 로그에만 남음</span>`

장식용 클래스를 새로 만들지 않는다. 목업 안에서만 필요한 최소 인라인 스타일은 허용한다.

## 6. 단계 설계

세 phase로 묶는다. phase 이름은 모드에 따라 다르다.

| | phase 1 | phase 2 | phase 3 |
|---|---|---|---|
| 개념 모드 | 왜 필요한가 (없을 때의 문제) | 핵심 구조 (개념 하나씩) | 무엇이 달라지나 (효과·비용·흔한 오해) |
| 구현 모드 | 사전 준비 | 처리 흐름 | 완료·후처리 |

개념 모드 phase 3는 **역할**(효과·비용·흔한 오해)만 고정이고 표시 라벨은 고정 텍스트가 아니다. "무엇이 달라지나"는 코드·기능처럼 전후 비교가 뚜렷한 주제에 맞는 라벨이다. 통계·수치처럼 phase 3 내용이 "체감이 다른 이유", "같은 원리의 다른 사례" 같은 주의점·확장에 가까운 주제라면 "알아둘 점", "실전에서는" 등 내용에 맞는 라벨을 고른다. 단, 한 문서 안에서 그 phase에 속한 모든 단계는 같은 라벨을 쓴다(단계마다 phase 이름이 바뀌면 안 됨).

전체 5~9단계. 한 단계에 한 가지 일 또는 한 가지 개념만 담는다.

비개발 주제(수학·과학·경제 등)에서는 대학 과정에서 처음 접하는 용어·정리(예: 자연로그 e, 라스파이레스 지수, 극한, 편미분)를 독립 단계로 세우지 않는다. 꼭 필요하면 다른 단계 안에서 일반인이 이해할 수 있게 한 줄로 풀어쓰고 넘어간다. 한 문서의 단계는 "중학생이 순서대로 따라올 수 있는가"로 점검한다.

**코드 칸**

- 구현 모드: 5~15줄. 주석 없이 핵심만, 그대로 붙여 넣어 동작하는 수준. `file` 에 파일 경로를 적는다.
- 개념 모드: 3~10줄. 개념이 드러나는 최소 형태만 — 인터페이스 시그니처, 의존성 방향이 보이는 생성자, 데이터 모양 한 조각. **구축 순서를 설명하는 코드를 넣지 않는다.** 코드로 보여줄 게 없으면 `code` 를 비운다.

**결과 칸**

- 구현 모드: 그 단계 직후 실제로 보이는 것. 권한 팝업, 알림, DB 행, API 응답, 터미널 출력.
- 개념 모드: 그 개념이 **있을 때와 없을 때**의 대비, 또는 구체적 상황 예시 한 컷. 없는 UI를 지어내지 않는다.

## 7. 말과 코드의 눈높이

- **말(정의·설명·라벨)**: 초보자 기준. 전문 용어가 나오면 그 자리에서 한 줄로 푼다. 비유는 짧게 한 번만. 그래프 모양 비유(S자, 우상향, 계단식, 꺾이는 지점 등)는 그래프를 읽을 줄 안다는 전제가 있어 쓰지 않는다 — 대신 실제로 벌어지는 일의 시간 순서(처음엔 A, 그다음 B, 나중엔 C)로 서술한다.
- **코드와 데이터**: 눈높이를 낮추지 않는다. 의사코드나 `// 여기에 로직 작성` 같은 자리표시자는 금지. 이 규칙은 코드가 있는 기술 주제(대상 독자 = 개발자)에 한한다.
- 수학·과학·경제 등 코드 없는 비개발 주제에서는 설명문뿐 아니라 각 단계의 **개념 자체**도 일반인 기준을 지킨다. 정확성을 위해 학술 공식·표기(Σ, 극한식 등)를 그대로 옮기지 않는다.

"왜"는 5살에게, "어떻게"는 개발자에게 말한다.

## 8. 코드가 없는 주제

기술 주제가 아니면(예: "비가 오는 원리") `lang` 과 `code` 를 비우고 `result` 에 "이때 실제로 일어나는 일"을 짧은 문장으로 넣는다. 정의 블록과 나머지 구조는 그대로 간다.

## 9. 정확성

확인되지 않은 API 이름·함수 시그니처·설정 키를 지어내지 않는다. 특정 버전에서만 되는 방식이면 코드 근처에 버전을 적는다. 확신이 없으면 그 단계에 "확인 필요"라고 쓰고 그럴듯하게 채우지 않는다.

URL도 같다. 확인되지 않은 링크를 지어내지 않고, 상세 페이지를 모른다고 공식 문서 홈·목차로 대체하지 않는다. 참고 링크는 10절 규칙을 따른다.

## 10. 참고 링크 (links.html)

문서 맨 아래 "참고 링크" 섹션(`<h2>`)에 들어갈 HTML 조각. 셸의 `<!--__LINKS__-->` 자리에 주입된다. **검증 시도(10-1~10-2) 자체는 사실 주장이 있는 모든 문서에서 필수다 — 생략 대상이 아니다.** `links.html`을 만들지 여부만 결과에 따라 갈린다: 실제로 찾아보고 검증까지 마친 링크가 1개 이상이면 만들고, 다 찾아봤는데도 0개면 만들지 않는다(`build.py`가 섹션을 통째로 제거). **찾아보지 않은 것을 "0개"로 셈해서 이 조건으로 건너뛰지 않는다.**

섹션 제목은 "참고 링크"지만 역할은 **근거**다. "더 읽어볼 거리"가 아니라, **정의 블록과 단계에서 한 핵심 주장을 실제로 뒷받침하는 글**만 넣는다. 각 링크는 이 문서의 어떤 문장이 왜 맞는지를 확인해 줄 수 있어야 한다. 주제와 관련은 있지만 우리가 한 말과 직접 이어지지 않는 글은 넣지 않는다.

### 10-1. 무엇을 고르나

1. 문서를 다 쓴 뒤, 정의 블록·단계에서 한 **사실 주장**을 3~5개 추린다(예: "의존성은 항상 바깥에서 안으로 향한다", "읽기 모델은 도메인 규칙이 없다", "이벤트 소싱과 자주 함께 쓴다").
2. 각 주장을 뒷받침하는 1차 출처를 찾는다. 한 링크가 여러 주장을 덮어도 된다. 목표는 **주장 커버리지**이지 링크 개수가 아니다.
3. 같은 주장을 뒷받침하는 후보가 여럿이면 아래 우선순위로 고른다. 공식 문서(1·2)가 최상위, 그 아래는 **국내 자료를 위에** 둔다(3 국내 실무 사례 > 4·5 해외 중심).

| # | tier | 뜻 |
|---|---|---|
| 1 | 한국어 공식 문서 | 그 대상을 만들고 관리하는 주체가 낸 한국어 문서 |
| 2 | 영문 공식 문서 | 같은 주체의 영문 문서 (한국어판이 없을 때) |
| 3 | 국내 실무 사례 | 우아한형제들·토스·당근 등 국내 현업 엔지니어링 블로그의 도입·구현기 |
| 4 | 기업 아키텍처 문서 | MS·AWS·Google 등 대형 플랫폼 기업의 설계·패턴 가이드 |
| 5 | 전문가 아티클 | Martin Fowler·Kent Beck 같은 거장, 또는 학계 권위자의 글 |
| 6 | 일반 참고 | 한국어 위키백과·표준화기구·교과 수준 자료. **표준·프로토콜·과학처럼 소유 기관 문서 + 교과 지식이 섞인 주제에서, 논쟁 없이 정설로 굳은 기본 동작**(예: CSMA/CA, SSID, 광합성 단계)의 근거로만 쓴다. 해석·의견·최신 기능에는 쓰지 않는다 |

**"공식 문서"(1·2번)의 뜻** — 그 대상을 만들고 관리하는 주체가 낸 문서일 때만 공식 문서다.
- 제품·라이브러리·표준(React, Kubernetes, OAuth2 RFC, PostgreSQL 등): 그 프로젝트/표준 단체의 문서 = 공식 문서.
- **소유자가 없는 패턴·개념**(CQRS, 헥사고날 아키텍처, DDD, SOLID, 이벤트 소싱 등): 공식 문서는 **존재하지 않는다.** 1·2번을 비우고 3·4·5번으로 채운다. 회사의 패턴 가이드(예: Microsoft Azure Architecture Center의 CQRS 글)는 '공식 문서'가 아니라 **기업 아키텍처 문서**(4번)다. 개념을 처음 제시한 사람의 글(예: CQRS는 Greg Young)은 **전문가 아티클**(5번).

- **상위 순위가 몇 개 나왔다고 거기서 멈추지 않는다.** 아직 근거가 안 붙은 주장이 남아 있으면 3·4·5번을 `WebSearch`로 실제로 찾아본다(예: `"<주제>" 우아한형제들`, `"<주제>" tistory`, `"<주제>" velog`, `"<주제>" AWS 아키텍처`). 우리 주장을 뒷받침하는 국내 실무 사례(3번)가 있으면 우선해서 넣는다.
- 한 순위에서 여러 개를 넣어도 된다 — 단, 각 링크가 **서로 다른 주장**을 받칠 때만. 같은 주장에 출처 2개를 겹쳐 달지 않는다(예: 공식 문서 홈페이지의 다른 소절 두 개는 하나로 친다).
- 다 뒤졌는데도 검증 통과가 2개 이하면 그것만 넣는다 — 억지로 못 미더운 링크를 끼우지 않는다. 하지만 "안 찾아봐서 2개"는 안 된다.

**비개발 주제**(예: "비가 오는 원리", "인플레이션")는 3·4·5번 태그가 안 맞는다. 다음으로 바꿔 쓴다 — ①한국어 기관·교과 자료 ②영문 기관·교과 자료(NASA, 대학 등) ③국내 해설(언론·기관·전문가) ④해외 해설 ⑤한국 블로그 글. 1·2번은 기상청·한국은행 같은 기관의 **특정 문서**로 채운다.

### 10-2. URL 할루시네이션 방지 (필수)

1. **그 주제를 직접 다루는 특정 페이지의 전체 URL만 링크한다.** 문서 홈·도메인 루트·카테고리/목차 페이지로 대체하는 링크는 **금지**한다. 상세 URL을 확실히 모르면 그 링크는 넣지 않는다.
   - ❌ `https://ko.react.dev/`  ⭕ `https://ko.react.dev/learn/synchronizing-with-effects`
2. **공식 문서는 먼저 한국어 로케일을 시도한다.** 영문 URL을 찾았으면 `WebFetch`로 한국어판이 있는지 확인한다:
   - 로케일 세그먼트가 있으면 바꾼다 — `/en-us/`→`/ko-kr/`, `/en-US/`→`/ko/`, `?hl=en`→`?hl=ko`, `react.dev`→`ko.react.dev`.
   - **로케일 세그먼트가 아예 없으면 호스트 바로 뒤에 `/ko-kr/`(또는 `/ko/`)를 끼워 본다** — 예: `bluetooth.com/about-us/x` → `bluetooth.com/ko-kr/about-us/x`. 많은 사이트가 기본(영문) URL엔 로케일을 안 붙인다.
   **본문 문단까지 실제로 한국어로 번역됐는지** WebFetch 프롬프트에 명시해 확인한다 — 네비게이션·일부 문구만 번역되고 본문은 영어인 페이지(예: `wi-fi.org/ko/*`)가 흔하고, "한국어 페이지냐"고만 물으면 속는다. 본문이 한국어면 그것을 **한국어 공식 문서**(1번)로 쓰고 영문판은 넣지 않는다(기계 번역도 인정). 본문이 영어면 영문 URL을 **영문 공식 문서**(2번)로 쓴다.
3. **URL을 패턴으로 조합·추측하지 않는다.** 알고 있는 다른 경로를 변형해서 만들지 않는다. (로케일 스왑은 예외 — 반드시 WebFetch로 확인한다.)
4. **후보 URL은 전부 `WebFetch`로 확인한다.** 정상 응답이고 페이지 제목·본문이 그 주제를 실제로 다루는지 본다. URL을 찾을 때는 `WebSearch`를 쓰고, 찾은 URL도 `WebFetch`로 재확인한다.
5. **확인 못 했거나 홈/목차 수준인 URL은 버린다.** 링크로 넣지 않는다.
6. **로그인·결제·회원 전용 페이지는 제외한다.** 비공개 카페 글, 멤버 전용 Medium 등.

### 10-3. 근거를 못 찾을 때

- 어떤 주장의 근거를 아무리 찾아도 없으면, 그건 그 주장이 불확실하다는 신호다. 9절대로 그 문장을 누그러뜨리거나 뺀다 — 근거 없는 단정을 남기고 링크만 생략하지 않는다.
- 검증 통과 링크가 1~2개면 그것만 싣는다. 검색어 안내·"~를 찾아보세요" 같은 대체 문구를 **절대 넣지 않는다.**
- **실제로 `WebSearch`/`WebFetch`를 돌려서** 검증 통과 링크가 0개로 확인됐을 때만 `links.html`을 만들지 않는다. → 섹션 자체가 산출물에서 빠진다. 빈 섹션이나 안내 문구를 남기지 않는다.

### 10-4. 형식

```html
<ul class="refs-list">
  <li>
    <span class="tier">한국어 공식 문서</span>
    <a href="https://…(WebFetch로 확인한 상세 URL)" target="_blank" rel="noopener">문서 제목</a>
    <span class="desc">이 글이 뒷받침하는 주장 — 예: "읽기 모델에 도메인 규칙을 두지 않는다는 원칙의 출처"</span>
  </li>
</ul>
```

`<ul class="refs-list">` 하나만 쓴다. `definition.html`처럼 `/tmp/eli5-build/<slug>/links.html`에 저장한다.

## 11. 완료 전 점검

- 주제가 여러 개일 때 파일 구성 방식(단일 파일 vs 여러 개의 파일)을 확인했는가 (이미 명시된 경우 제외)
- 단일 파일 또는 여러 개 파일의 각 주제별로 적절한 모드를 확인했는가
- 다중 파일인 경우 전체 개념을 통합 정리한 마크다운(.md) 아티팩트를 함께 생성했는가
- 로컬 환경에서 브라우저 1-클릭 실행이 가능한 HTTP 링크 및 로컬 프리뷰 서버를 제공했는가
- 마크다운 및 텍스트에 불필요한 장식용 이모지/아이콘이 배제되었는가
- 한 줄 정의와 `<dl>` 3항목이 모두 있고, 그것만 읽어도 개념의 정체가 잡히는가
- 비개발 주제일 때, 각 단계 제목/요약을 그 분야 비전공자가 읽어도 막히지 않는가
- 정의 블록에 개별 구성 요소 설명이 섞이지 않았는가 (그건 단계의 몫)
- 각 구성 요소가 단계에서 하나씩 설명되고 있는가
- 배치 형태를 4-1 표에서 고르고 그 근거가 있는가 — 순서가 없는 주제를 가로로 늘어놓지 않았는가
- 셸을 재작성하지 않고 `build.py` 로 주입했는가
- 개념 모드인데 구축 순서 설명이 섞이지 않았는가
- 모든 `nodes` / `edges` 값이 SVG에 실제로 존재하는가
- SVG에서 글자가 노드 밖으로 나가거나 요소가 겹치지 않는가
- 참고 링크 검증을 실제로 시도했는가 — `WebSearch`/`WebFetch` 호출 없이 "0개"로 처리하고 건너뛰지 않았는가
- (검증 통과 링크가 있으면) `refs-list`의 모든 URL을 WebFetch로 확인했는가 — 전부 그 주제를 다루는 특정 문서이고 홈·도메인 루트·목차 URL이 하나도 없는가
- 각 링크가 이 문서에서 한 특정 주장을 뒷받침하는가 — 주제만 겹치는 '읽을거리'를 넣지 않았는가. `desc`가 무슨 주장을 받치는지 말하는가
- 근거를 못 찾은 주장을 단정으로 남기지 않았는가 (9절대로 누그러뜨렸는가)
- 공식 문서에 한국어판(`/ko-kr/`, `/ko/`, `ko.` 등)이 있는데 영문판을 넣지는 않았는가
- '공식 문서' 태그를 붙인 링크가 정말 그 대상을 만든 주체의 문서인가 — 소유자 없는 패턴·개념에 회사 가이드를 '공식 문서'로 달지 않았는가
- 아직 근거 안 붙은 주장이 있으면 국내 실무 사례·기업 아키텍처 문서·전문가 아티클을 WebSearch로 실제 찾아봤는가 ("안 찾아봐서 부족"이 아닌가)
- 검증 통과 링크가 0개면 `links.html`을 안 만들었는가 — 검색어 안내·"찾아보세요" 같은 대체 문구를 넣지 않았는가
- 링크가 로그인·결제 전용은 아닌가
- `tier` 라벨이 10-1 표의 이름(한국어 공식 문서 / 영문 공식 문서 / 국내 실무 사례 / 기업 아키텍처 문서 / 전문가 아티클 / 일반 참고)과 일치하는가 (비개발 주제는 10-1의 대체 태그). '일반 참고'는 정설로 굳은 기본 동작에만 썼는가
- 단일 파일인 경우 빌드 직후 기본 브라우저에서 고유 슬러그 HTML 문서를 즉시 오픈했는가 (`open /tmp/eli5-build/<slug>.html`)
